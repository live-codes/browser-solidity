# Taste
- Prefers new language/runtime integrations to start as a standalone proof-of-concept spike — a simple static HTML page — before wiring anything into the main project. Confidence: 0.7
- Wants compiler/runtime support to run entirely client-side in the browser, with no servers or server-side compilation involved. Confidence: 0.7
- Prefers reusing existing in-repo `@live-codes/*` packages and the established LiveCodes language-package pattern (e.g. `createCompiler`/`run` API, bundled assets, IIFE/global builds for classic workers) over ad-hoc spikes or external CDN dependencies. Confidence: 0.7
- When adding language support, wants it packaged to match a named sibling package faithfully — mirror its layout (`src/` + `bin/` + `scripts/` + `dist/` + `test/` + `example/`), entry points, `copy-assets` CLI, IIFE bundles and API/test conventions — rather than inventing a new shape. Confidence: 0.65
- Draws an explicit boundary around exploratory work: while a capability is still a POC, nothing is to be written into the target/production repo (e.g. "Do not write anything to LiveCodes for now") — the deliverable is the reusable package plus design answers, not an integration. Confidence: 0.6
- When deciding how a new integration should behave, wants the recommendation grounded in how practitioners of that domain actually work (the field's reference tool and the expected user loop) and in existing project affordances, rather than invented UI or purely technical reasoning; states when he lacks domain knowledge and expects the domain to be explained. Confidence: 0.5
- Prefers fixing broken local dev tooling (e.g. reinstalling a global package whose binary went missing) rather than working around it. Confidence: 0.55
- Once shared functionality is extracted into a reusable package, wants existing consumers (the original spike/POC/demo) rewired onto that package and the now-duplicated code deleted, rather than maintaining two implementations. Confidence: 0.65
- Communicates in terse, single-sentence directives and expects the agent to carry a change end-to-end — implement, verify it in the browser, update the docs — without asking for confirmation along the way. Approves a proposed multi-part plan (API changes plus tests) with a bare "yes", with no further qualification or review of the details. Confidence: 0.6
